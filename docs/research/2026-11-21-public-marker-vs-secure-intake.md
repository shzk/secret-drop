# Secret Drop — проверка «ввода секрета» через MCP Form и безопасного двухэтапного сценария

**Дата:** 21.11.2026. **Тип:** исследовательский тест, не изменение релиза.
**Исходник:** [shzk/secret-drop](https://github.com/shzk/secret-drop), `research/mcp-elicitation-20261121`.
**План:** [2026-11-21-form-value-visibility.md](../plans/2026-11-21-form-value-visibility.md), **задача:** TickTick `6b01c4f28f08fe236af3e5e5`.
**Базовый релиз:** Secret Drop Codex `0.6.0`, принят ранее и не изменён.

## Результат по существу

**Обычная встроенная MCP Form не является безопасным полем для API-ключа.** Согласно [MCP Elicitation specification 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation) сервер **MUST NOT** запрашивать пароли, API keys или access tokens через `mode=form`; для такой чувствительной операции предусмотрен `mode=url` (либо иной внеполосный защищённый механизм, такой как уже принятый локальный AppKit Secret Drop). [Официальный TypeScript SDK](https://ts.sdk.modelcontextprotocol.io/v2/servers/elicitation) дополнительно предупреждает: содержимое формы идёт через клиент и может оказаться в контексте модели.

Проверены две **разные** ветки поведения. Никаких настоящих ключей не использовалось.

## Эксперимент A — публичный тестовый маркер через Form

В исследовательском [MCP stdio probe](../../research/elicitation-host-pilot/stdio_probe.py) появился отдельный инструмент `probe_demo_value_visibility`. В форме допустимо выбрать **только буквальную публичную строку** `PUBLIC_SYNTHETIC_DEMO_123`, не являющуюся секретом или токеном доступа. Посторонние поля, произвольные значения и поля, похожие на credentials, отклоняются; входные значения из ошибки не выводятся.

**Тест на настоящем Mac Codex app-server `0.163.0`** (client simulation, **без** генерации моделью и **без** Codex Desktop UI):

```text
INIT_ACK=yes
THREAD_STARTED=yes
ELICITATION_EVENT=yes
ELICITATION_MODE=form
ELICITATION_SERVER_MATCH=True
CALL_RETURNED=True
FORM_ROUTED=True
PUBLIC_DEMO_MARKER_IN_TOOL_RESULT=True
```

В реальном ответе MCP-инструмента присутствует открытая строка `PUBLIC_SYNTHETIC_DEMO_123`. Этот факт доказывает **отсутствие изоляции значения от MCP-клиента и результатов инструментов**. Поскольку в тесте модель не запускалась, нельзя утверждать, что именно модель прочитала или сохранила строку; однако результат инструмента потенциально видим ей.

## Эксперимент B — Form только для назначения, AppKit для фиктивного значения

[Синтетический двухэтапный тест](../../research/elicitation-host-pilot/test_form_then_safe_intake.py):

1. Исследовательский MCP Form с `destination=config/.env.local`, `confirm=True` возвращает только разрешение и несекретные метаданные.
2. Используется **реальная реализация `request_secret` из принятого `codex/secret-drop/server/mcp_server.py`**. Её `native_dialog` в этом *юнит-тесте* замещён локальной имитацией AppKit, возвращающей только фиктивную строку `FAKE_LOCAL_FIXTURE_ONLY_2026`.
3. Реальный локальный writer создаёт `config/.env.local` внутри защищённого временного проекта с `0600`; значение проверяется только внутри теста на локальном диске.
4. В результате MCP-инструмента присутствует **имя переменной и успешный статус**, но нет фиктивного значения. Проверено отдельно, что его нет и в возвращённом результате Form.

**Важная граница:** здесь тестировалась связка **на уровне кода и файловой операции**, а не анимация/реальное появление двух окон подряд в Codex Desktop. AppKit возвращал фиктивный ответ через mock, а не от настоящего человека. Реальная AppKit-форма принята пользователем в прежнем E2E версии `0.6.0`; тот успешный результат не переобъявляется новой проверкой.

Начальная тестовая директория macOS находилась под алиасом `/var`→`/private/var`, и trusted-root validation правильно отклонил её. Тест был исправлен на канонический `Path(td).resolve()`; **саму защиту проекта не ослабляли**.

## Решение

- **Не добавлять** в Secret Drop поле API-ключа напрямую во встроенную MCP Form: это нарушение нормативных ограничений и неправильный trust boundary. Даже поле `password`/замаскированный ввод не исправляет транспортную проблему.
- **Безопасный вариант без нового веб-сервиса:** встроенная форма Codex **только для несекретных сведений** (назначение, причина, подтверждение), а реальное значение вводится в локальный проверенный AppKit Secret Drop. При этом это **два интерфейсных шага**, и дополнительная форма может не давать выигрыша в удобстве; текущий AppKit уже показывает полное назначение и требует подтверждения.
- **Для цели «ввод прямо в карточке без отдельного окна»** нужна отдельная архитектурная оценка внешнего доверенного URL-mode с идентификацией пользователя, проверкой происхождения, отсутствием токенов в URL и точной политикой хранения, либо другой документированный защищённый канал. Это не следует автоматически из наличия MCP Apps iframe.
- Пока **GO только на исследования**, не менять установленный `secret-drop-codex@secret-drop-tkrv` `0.6.0`, `main`, пользовательские MCP-настройки или upstream PR #2; дальнейшая продуктовая интеграция требует отдельного решения об UX и защите.

**Воспроизведение (Mac, из research worktree):**

```sh
PYTHONDONTWRITEBYTECODE=1 python3 research/elicitation-host-pilot/codex_appserver_smoke.py --public-demo
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s research/elicitation-host-pilot -q
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s codex/secret-drop/tests -q
git diff --check origin/main...HEAD
```

**Установка/конфигурация:** глобальный тестовый MCP был ранее удалён с побайтовой сверкой `~/.codex/config.toml`. Этот эксперимент использовал только краткоживущий app-server с process-scoped настройкой и временные локальные fixture файлы, которые удаляются после теста.
